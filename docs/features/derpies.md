# Derpies filter

The derpies filter is a passive handler (the thirteenth, `internal/handlers/derpies`) that silently deletes Derpie's gimmick posts. It never sends a bot message, reaction, or `#the-gulag` notification — `DeleteMessage` is the MESSAGE flow's only outgoing action call (the nickname flow's reset PATCHes the guild member — see Nickname flow; a reply/quote-reply message additionally makes one data GET to fetch the referenced message), and every failure path is log-only.

## Gates (checked in this order)

1. Feature flag `derpies` (`features.IsEnabled` silent flavor: off on any error, including a missing row).
2. Guild guard (DMs are ignored).
3. Author-ID gate — the checked `core.DiscordID` conversion of the author ID must hit `Config.DerpiesUserIDs` (parsed from `TUGBOT_DERPIES_USER_IDS`, comma-separated, malformed parts skipped — same semantics as `SLOW_USER_IDS`).

## Fast path

Per message, the handler fetches `derpies_gimmicks` (a plain list SELECT — the table has no index, a seq scan is fine at this size), tokenizes the content into a FOLDED ASCII token space (each token NFD-decomposed, combining marks AND format characters (Cf — zero-width space / word joiner / ZWNJ) dropped, lowercased, non-decompose-able lookalike letters folded to ASCII via a conservative confusable map (Cyrillic/Greek letters, fullwidth, Arabic-Indic digits, ı/ə/ß→ss), `strings.Fields`, edge-punctuation trimmed), and deletes on any exact token hit — no pi RPC ask. The token set is the union of the posted message and, when fetchable, the one-hop referenced message's content — a reply re-quoting a seeded word is a fast-path hit without retyping it (the referenced fetch is one REST GET via the `discordOps` seam). A unicode respelling of a seed word (e.g. `świft`, which folds to `swift`) is a fast-path hit; so is a non-decompose-able respelling (e.g. `zwіft` with Cyrillic `і`, `z\u200bwi\u200bft` spaced with zero-width spaces) — the confusable fold was added 2026-09-07 because such tokens previously leaked structurally (no valid verdict existed for them: the base word is not a folded token and the variant is not wordValid).

The token set ALSO carries **collapsed runs of single-rune tokens** (the SPLIT evasion, ADR 0009, 2026-09-17): a maximal stretch of consecutive tokens whose folded form is a single rune contributes its space-free concatenation (a run of `>=2`, capped at 32 runes; a pure-punctuation token between letters does NOT break the run, a multi-rune token does). So `z w i f t` yields `{z, w, i, f, t, zwift}` and a seeded `zwift` is a zero-ask fast delete. The collapse is additive (the single-rune tokens stay) and is shared by the fast path, the step-9 gate, and the nickname flow.

**Phrase fast match (ADR 0010).** After the word fast path, the handler also fetches `derpies_gimmick_phrases` (manual-only — the LLM never writes here; `source='manual'`) and matches each stored phrase as an EXACT consecutive run of the folded token sequence (each phrase token `FoldToASCII`-folded + edge-punctuation trimmed, so a curated `Buy me a bike` matches the folded `buy me a bike`). The phrase window slides over the posted content and the referenced content SEPARATELY (never concatenated — a phrase spanning the message/reply boundary must not match); embed titles are NOT scanned for phrases (v1). An exact consecutive match is a zero-ask fast delete (a `derpies_decisions` row with `path='fast'`, `word=<phrase>`). A SPLIT word inside a phrase is NOT fast-matched (v1 is exact-consecutive only — it falls to the slow path). A `listPhrases` fetch failure degrades to the slow path (log, never act on a half-loaded list).

## Referenced messages

A reply/quote-reply message (`MessageReference` with a message ID) fetches one hop of the referenced message — a single REST GET via the `discordOps` seam (mention parity; chains are not followed). On fetch failure (already deleted, rate-limited) the flow logs and continues WITHOUT a reference — never aborting the flow. When fetched: the reference's text joins the fast-path token union, its images join the download union, and its content is quoted in the pi ask between the `<<<REFERENCED MESSAGE` / `REFERENCED MESSAGE>>>` markers (the shipped prompt's `{{REF}}` marker substitutes that block) — so a gimmick living only in the quote is both fast-path catchable and LLM-visible.

## Gif handling

**Embed titles join the judged text — the observed survival vector.** The observed survival vector is a Klipy `gifv` embed: the message text is a bare URL; the brand word lives in the embed TITLE ("Indoor Cycling with Zwift Virtual Ride", "Peloton Lady Kendalltoole" — `peloton` is LLM-learned, `source='llm'`, 2026-09-09). Every non-empty `MessageEmbed.Title` (at most 10 titles — Discord's per-message embed cap — each trimmed to 200 RUNES; `Description`/`Provider`/`Footer` deliberately excluded) joins the FAST-PATH token union together with the posted + referenced content (the title is part of what was posted — a titled link the user chose to post counts as posted content; the stance is adversarial, so false negatives are the worse error): a titled link carrying a list word fast-deletes with ZERO asks. The titles also join the slow path: the `{{EMBED}}` marker substitutes the "TITLES OF MEDIA EMBEDDED WITH THE MESSAGE" block (a known word in a title counts as if typed), and the step-9 gate reuses the SAME token union — a non-empty title makes the post "have text" for the gate (identical to typed text), so a frame-anchored verdict word on a titled post is rejected. `{{EMBED}}` is OPTIONAL — a template lacking it degrades by omission.

**Uploaded animated GIFs (the `image/gif` attachment leg).** Each animated attachment expands IN-PROCESS (stdlib `image/gif` — zero new dependencies, no new seam) into at most 8 evenly-spaced JPEG q80 frames: the input is capped at 16MB BEFORE decode (an over-cap input degrades to the status-quo raw send — logged with the byte length, the decode work is never attempted), and the DECODED DIMENSIONS are capped at 16 megapixels of logical screen (4096×4096) — read via the global `gif.DecodeConfig` header BEFORE the full decode (a uniform large-screen gif compresses to KBs on disk, so the byte cap alone cannot bound that decode work — an over-cap screen degrades to the status-quo raw send with its own logged arm naming the dims bound, distinct from the bytes-cap arm), the 60-frame selection cap after), up to 60 frames walk from the stream; each selected frame is composited onto the FULL canvas before encoding (a partial-rectangle delta frame is never encoded as-is, so the model can't miss the burned-in gimmick text: decoded frames arrive in in-canvas coordinates — this toolchain's `DecodeAll` retains a frame's `Bounds().Min` offset — and `draw.Over` on a persistent canvas emulates the GIF keep-previous disposal, transparent palette entries preserving the canvas beneath); a selected canvas equal (32×32 grayscale, strided sampling, tolerance 8) to the previously added canvas is dropped (a looping gif emitting fewer than 8 frames is correct). A single-frame, undecodable, or over-cap GIF degrades to the STATUS-QUO raw send (log, never abort the flow); a per-frame encode failure is logged and that frame is skipped. The frames join the SAME single ask as everything else — never a separate ask.

**`gifv` embed videos (mp4/webm — the govid leg).** EVERY `gifv` embed whose `MessageEmbed.Video` URL is non-empty plans that video URL (isSafeURL-guarded; the mime is left IRRELEVANT because the decoder sniffs the container; a non-`gifv` embed carrying a video is NOT planned). Download: an 8MB hard cap (the Content-Length cap short-circuits BEFORE the read; a non-2xx status is an error and the body is NOT read — a 4xx/5xx body can never be a decodable clip; a body LONGER than the cap is an error even when the Content-Length lied), 10s client. Decode via `github.com/liqmix/govid` — PURE Go (no cgo, no ffmpeg binary), bit-exact for H.264/High and VP8 — behind the `videoFrameDecoder` seam (wired in `New()`; tests wire a fake or leave it nil): container selection is a LENGTH-GUARDED magic-byte sniff (`ftyp` at offset 4 → mp4 + H.264; EBML `0x1A45DFA3` at offset 0 → webm + VP8; anything else → unsupported → warn + skip), then ≤8 frames by SEEK (keyframe-accurate: `codec.Flush()` immediately post-seek discards the H.264 reorder buffer, so the first decoded frame is the seek-target — not a stale buffered frame — and SPS/ref state does not carry across), walking up to 32 packets after a seek, with a bounded sequential fallback (up to 600 packets walked, taking the last usable frame) when a seek-window yields nothing. ANY download error, a nil decoder, a decoder error, an unsupported container, or a zero-frame result degrades to THUMBNAIL-ONLY (the thumbnail, if planned, rides on its own entry) — log + skip, never abort. Per-sample failures (a failed seek, a frame that yields nothing, an undecodable/partial frame) log + skip that sample; the remaining frames still ride. The webm/VP8 arm ships with per-sample degrade only (the shipped fixture covers the mp4/H.264 arm end-to-end).

**Joining ONE ask.** ALL frames — uploaded-gif and gifv-video, posted + referenced, URL-deduped — append to the images of the ONE existing `AskWithImages` call (no new asks) and pass through the pirpc per-ask image guard unchanged (byte-identical dedupe, >1MB/>2048px resize to 2048/JPEG q80, 12MB raw cap). The `{{GIFS}}` marker (substituted only when at least one gif frame was emitted) substitutes the "up to 8 SAMPLED frames" guidance — "gifs loop and change over time, so a gimmick's word can appear in ANY frame; judge all of the frames too". `{{GIFS}}` is OPTIONAL — a template lacking it degrades by omission (a pre-feature live DB row keeps working; `validTemplate` guarantees a marker-less row can never break the flow).

## Nickname flow

A gated member's `GUILD_MEMBER_UPDATE` is judged the same way as a message (feature-flag-gated, same author-ID gate): fast-path token match against `derpies_gimmicks`, then one pi-RPC verdict on a miss. `GUILD_MEMBER_UPDATE` fires for ANY member change (role, mute, nick…), so change detection runs on an in-process per-member cache — an event whose nick equals the cached value is skipped (no nick change, no wasted RPC). Resets are per-member coalesced: at most ONE reset attempt per 60-second window, and success OR failure marks the window (429 discipline — a failed attempt is never retried inside it). The bot's own write is never re-judged: a successful reset records the reset value in the cache BEFORE the gateway echo arrives, so the echo (nick equal to the cache) is skipped by the same change-detection check.

The reset now SETS the guild nick to the fixed neutral name `Derpies` (const `derpiesNickReset`) — one of the flow's outgoing REST calls (`PATCH /guilds/{guild}/members/{member}` with `{"nick":"Derpies"}` via the `discordOps` seam) — a fixed-value write replacing the old null-clear, which would expose the member's GLOBAL display name, a name the bot has no API to modify. The nick is judged by the **score model** (ADR 0010): `parseVerdictScore` (the same parser as the message flow — a missing SCORE line is `unrecognized` → cache the nick, do nothing), then the same two-band matrix with the action being a nick **reset** (not a delete): `score < 40` → do nothing (cache the nick, no reset); `40 ≤ score < T` → learn the word (if valid+anchored to the nick), no reset (cache the nick); `score ≥ T` → learn the word (if valid+anchored) + reset via `resetNow`. The learn gate is the same two-arm gate (`wordValid` + folded-token-in-nick, ADR 0008) with the `wordLike` anchor fix (an all-emoji nick — no word-like tokens — skips the anchor requirement, so a valid word passes and the score decides). The `lastNick` change-detection cache is written on every JUDGED terminal arm (the `score < 40` and `40 ≤ score < T` arms call `saveNick`; `score ≥ T` goes through `resetNow`) so a later same-nick event is skipped; the pre-matrix failure arms (list fetch failed, pi unavailable, ask failed) do NOT cache (a transient failure stays retryable). The nickname flow is NOT logged to `derpies_decisions` (v1 — a nickname is not a message); its decisions stay in the slog log. Phrase matching is NOT added to the nickname flow in v1 (a nickname is a short display name; the word fast path covers it).

## Message edits

Every `GUILD_MESSAGE_UPDATE` by a gated author re-runs the FULL create flow on the updated content — the update payload's content/attachments are judged as-is (fast path, images, one-hop reference, one slow ask, learn, delete all carry over; at most one list SELECT + one pi ask per edit; burst profile = creates). An edit is origin-agnostic — there is no repeat-delete arm: a re-posted image is re-judged in a fresh ask like any other content (see the repeat-image note under Known limitations). A bare payload — no text, no attachments, AND no embeds — is fetched by channel+id through the `channelMessageRetrieve` seam; fetch failure degrades (log + skip), never aborts; the fetched message must carry an Author and a GuildID (both guarded — a nil-Author fetched message is logged + skipped, never panicked on). The fetch trigger is a strict deviation from the gokupoll precedent (mod.rs:126-136), stated and not implied: gokupoll fetches on empty content ALONE; here an image-capable payload (attachments OR embeds present — the flow's imageURLPlan reads both) is judged in place instead of fetched (fewer REST calls — the image leg is identical either way; a judged-in-place payload re-downloads its images through the same seam). There is no echo recursion: the bot never edits messages.

## Slow path (the score model, ADR 0010)

A miss sends ONE pi RPC ask (the 300 s deadline lives in the pi RPC package; the event thread is never held — each message spawns its own flow goroutine) — via `AskWithImages` when the message's downloaded images (attachments + embed images, mention-mirror leg, per-URL failure logged + skipped, degrades to a text-only ask when nothing downloads) exist — the shipped prompt's `{{IMAGES}}` marker substitutes that images line — plus the fetched referenced content, when a reply/quote was resolved. The prompt fences the raw message in `<<<UNTRUSTED MESSAGE` blocks, injects the known-word + known-phrase lists (sorted, byte-stable), names the evasion techniques as an instance class (respelling / unicode lookalikes / punctuation-wedged / split / hidden / squeezed / asking-phrasing / quoting / images / **emoji-encoding** — a combo of emojis whose COMBINED meaning is a roster solicitation; a single emoji is harmless alone, the combo is the gimmick), and asks for a **calibrated score** rather than a binary call: the LLM returns `SCORE:<0-100>` (always) + an optional `WORD:<anchor>` (only when the message carries a real trace, score ≥ 40). The scoring scale is 4 bands (90-100 unambiguous solicitation; 60-89 clear trace; 40-59 possible trace; 0-39 no meaningful trace), and the prompt's stance is adversarial — when torn between two bands, score toward the HIGHER side (a false negative is the worse error for this user). The pi RPC always appends the anti-injection system fallback.

**Parsing + the two-band matrix.** `parseVerdictScore` scans all lines (TrimSpace'd — the prompt displays the reply format indented): the first `SCORE:<0-100>` line (case-insensitive, `\s*` after the colon) is the score; the first `WORD:<...>` line's remainder (trimmed, lowercased) is the word (a spaced SPLIT answer is captured and handed to `foldVerdictWord`). No valid SCORE line → `unrecognized` (log, do nothing — a legacy `CLEAN`/`GIMMICK` verdict carries no score line and is unrecognized here; the nickname flow parses the same way). The score is thresholded against a **two-band matrix** with a live dial `T` (the delete threshold, read per message from the single-row `derpies_config` table — `configThreshold` targets the row explicitly, `WHERE id = 1`, the singleton enforced by a `CHECK (id = 1)`; a DB error or missing row degrades to the default `defaultThreshold = 50`, the store clamps a valid-but-out-of-range read to 41-100):

```
score < 40:            do nothing (no learn, no delete)
40 ≤ score < T:        learn the word (if valid+anchored); no delete
score ≥ T:             learn the word (if valid+anchored) + delete
```

**Learn and delete are INDEPENDENT.** Learn is gated on `score ≥ learnFloor` (40, a code constant) and runs the two-arm gate (below) on the FOLDED verdict word — a word rejection only stops the LEARN, it never blocks a score-driven delete. Delete is `score ≥ T` — a delete failure is LOG ONLY (a word learned in the learn step stays learned; the failure overrides any word-rejection reason on the decision row with `reject_reason='delete failed'`). A failed `addGimmick` insert is recorded as `learned=false` + `reject_reason='learn failed'` (never as a successful learn).

**The two-arm gate (ADR 0008, unchanged in shape).** Before a verdict learns, the verdict word is FOLDED — and its whitespace COLLAPSED (`foldVerdictWord`, ADR 0009: a SPLIT verdict `z w i f t` normalizes to `zwift` before the gate) — through the same token fold as the message tokens, and the two-arm sanity gate must pass on the FOLDED word: **arm (a) ASCII** — `wordValid` (`^[a-z0-9]{2,32}$`) — plus the anchor requirement; **arm (b) non-ASCII** (ADR 0008) — for a word whose folded form is not `wordValid` (no-confusable scripts, e.g. Arabic خفيف), the word is accepted ONLY when it is text-anchored: a plausible word shape (letters-only, 2..32 runes) AND a verbatim folded token of the judged text. A shared prefix applies on both arms: a PURE digit string is never a valid verdict word. **The anchor requirement is the emoji fix (ADR 0010):** it applies only when the POSTED message carries **word-like** text tokens (`hasWordLikeTokens` — a token is word-like iff it's non-empty, not all-digit, and `wordValid` OR the non-ASCII shape). A mention snowflake (all-digit) / emoji-ref (colon) / pure-emoji token (folds to `""`) is NOT word-like, so a "mention + emoji" post (the observed dead end: `<@…> 💸 <:derpies:…> 🚵`) is judged like an image-only post — a valid ASCII word passes `wordValid` alone and the score decides (the LLM answers the most distinctive word of what the emojis MEAN, e.g. `zwift` for 💸🚵). The anchor CHECK itself still uses the UNION token set (posted + referenced + embed titles — the word may legitimately anchor to the quoted content); arm (b) stays text-anchored on the posted-message word-like scope (a word-less post has no word-like anchor, so the frame-only dead-end stays dead — ADR 0007 deliberately NOT relaxed). A hallucinated or coerced word can never enter the list. The stored/learned word is the FOLDED word (`INSERT ... ON CONFLICT (word) DO NOTHING`, `source='llm'`), then the message is deleted (if `score ≥ T`).

**The decision log.** Every judged message (and edit) writes ONE append-only row to `derpies_decisions` via a single `defer` placed right after the author-ID gate (pre-gate arms return before it → no row; a write failure is best-effort — logged, never aborts the action). The row records the path (`fast`/`slow`/NULL for a pre-matrix arm), the score + threshold (NULL when the arm never reached the matrix), the learned word, the learn/delete outcomes, and the rejection reason — so `read_derpies_decisions` (the MCP tool) shows operators exactly what was judged, what was learned/deleted, and why a word was NOT learned (a failed insert, a rejected word, an unrecognized verdict).

## Data

`derpies_gimmicks` (migrations `000002_derpies_gimmicks` and `000004_derpies_cog_words`): `id`, `word varchar(64) UNIQUE`, `source varchar(8) DEFAULT 'seed'`, `created_at`. Seeded words: `swift`, `zswift`, `bike`, `give`, `buy` (all `source='seed'`) plus the nine "cog" respellings `cog`, `cogs`, `coggs`, `c0g`, `c0gs`, `coq`, `coqs`, `kog`, `kogs` (all `source='seed'`) — fourteen seed rows total. The `features` table gains a `derpies` row via `ON CONFLICT (name) DO NOTHING` (lives already in prod; fresh DBs seed it OFF).

Migration `000005_derpies_score` adds three tables (ADR 0010):
- `derpies_config` — the operator's live dials, a SINGLE row (enforced by `CHECK (id = 1)`): `id`, `delete_threshold integer DEFAULT 50 NOT NULL` (the delete threshold `T`, `CHECK (BETWEEN 41 AND 100)` keeps `T > learnFloor`), `updated_at` (NOT auto-updated — an operator `UPDATE` of `delete_threshold` should also set `updated_at = now()`). Seeded `(1, 50)`.
- `derpies_decisions` — append-only, one row per judged message/edit: `id bigserial`, `message_id`, `channel_id`, `author_id`, `content`, `path` (NULL-allowed, `CHECK (path IN ('fast','slow'))` — NULL for a pre-matrix arm), `score` / `threshold` (NULL-allowed — NULL when the arm never reached the matrix), `word`, `learned` / `deleted` (booleans), `reject_reason` (NULL when no rejection), `created_at`. Two indexes: `(author_id, created_at DESC)` + `(created_at DESC, id DESC)`. A `NULL` `path` passes the CHECK (PostgreSQL evaluates a CHECK on NULL as satisfied). Read back via the `read_derpies_decisions` MCP tool (`Derpies.ReadDecisions` → `queryDecisions`, a parameterized `SELECT` with optional AND-combined filter clauses, `ORDER BY created_at DESC, id DESC`, `LIMIT` default 50 / clamp 500, `Since`/`Until` normalized to UTC before binding).
- `derpies_gimmick_phrases` — manual-only (the optimizer): `id`, `phrase varchar(300) UNIQUE`, `source varchar(8) DEFAULT 'manual'`, `created_at`. The LLM never writes here (curation is SQL-only in v1).

## Live prompt (DB)

The prompt template lives in the single-row `derpies_prompt` table (migration `000003_derpies_prompt`, `body` + `updated_at`), seeded byte-for-byte with the code default; the flow fetches it per message (one row SELECT — the same per-message-fetch shape as the feature flag, the gimmick list, and the config). Since ADR 0010 the prompt is **SCORE-format**: it asks for `SCORE:<0-100>` (always) + an optional `WORD:<anchor>` (only when the message carries a real trace, score ≥ 40), with a 4-band scoring scale, the `EMOJI-ENCODING` evasion technique, and the anchor rule relaxed to "the word must be a token of the message text AS IT APPEARS — EXCEPT when the gimmick lives ONLY in the emojis (the message has no other text words): then answer the most distinctive word of what the emojis MEAN".

**Three in-sync locations.** The prompt text lives in exactly three places that MUST stay byte-for-byte identical (modulo the SQL `''`-doubling for the two apostrophes, `filter's` → `filter''s`, `message's` → `message''s`): (1) the `defaultPromptTemplate` Go constant (the code fallback — a missing/invalid row falls back to it), (2) the `000003` seed (fresh DBs), and (3) the `000005` `UPDATE derpies_prompt` (the production flip). `TestMigration000003AppliesAndSeeds` (seed == constant) + `TestMigration000005AppliesAndSeeds` (`derpies_prompt.body == defaultPromptTemplate`) are the forever sync guards.

**Atomic deploy (the rollout constraint).** The prompt flip lives INSIDE migration `000005` (not a manual pre-deploy `UPDATE`): the deploy runs migrations then restarts, so the prompt, the config/decisions/phrases DDL, and the new code all flip in ONE atomic step. A manual pre-deploy `UPDATE derpies_prompt` would create a guaranteed slow-path-dead window (old code + new SCORE-format prompt → every verdict `unrecognized` → zero slow-path deletes/learns until the deploy completes; the reverse order — new code + old binary prompt — is equally dead, `hasScore=false`). Residual risk: a deploy that fails AFTER the migration applies but BEFORE the restart leaves the prompt SCORE-format while the old code still runs — the slow path is dead until a re-deploy. Manual rollback: `UPDATE derpies_prompt SET body = <previous binary prompt>, updated_at = now();` (the previous body is in git history / the pre-deploy DB).

Template contract: the literal `{content}` (code wraps the raw message in the `<<<UNTRUSTED MESSAGE` fence) and `{known}` (the sorted known-word list) are MANDATORY — a template missing either is INVALID and never used. `{{IMAGES}}`, `{{REF}}`, `{{EMBED}}`, and `{{GIFS}}` are OPTIONAL — an absent optional marker is fine, the element is simply omitted. A missing or invalid row falls back to the code-pinned default template — the filter never runs with a broken prompt (a fetch error warns; an invalid-but-present row falls back silently).

Edit path: `psql … UPDATE derpies_prompt SET body = '…';` — the next message picks it up (no deploy, no restart). Rollback = restoring the previous body text.

Blast radius: a prompt edit changes WHAT gets caught, never what may be learned/deleted without a verdict word — the learning gate (arm (a) `wordValid` on the folded word, arm (b) the text-anchored non-ASCII shape + folded-token-in-(posted-+referenced-+embed-title)-text, plus the all-digit prefix) stays the code-enforced backstop.

## Known limitations (intentional, per spec — delete-only, no rate limiting)

- **Unicode**: Latin-extended unicode respellings fold (NFD) into ASCII and are caught (fast-path seed hits / LLM-learnable). Non-decompose-able lookalikes in the conservative confusable map (Cyrillic а/б/в/е/і/о/р/т/у/х/ѕ/э, Greek α/β/δ/ε/ι/λ/μ/ν/ο/ρ/ς/σ/τ/υ/φ/χ/ω, fullwidth, Arabic-Indic digits, ı/ə/ɛ/ß, zero-width Cf chars) now fold too (fast-path hits). Letters with NO entry (the rest of a non-Latin script) still evade the fast path but are now LLM-catchable text-anchored (ADR 0008): a non-ASCII verdict word is accepted iff it is a verbatim folded token of the judged text. Remaining structural dead-ends: a message whose only roster text is a token with NO confusable folding AND no LLM-named token (the LLM's best answer is CLEAN and it passes) — and, for non-ASCII words, a frame-anchored word with no text tokens (the image-only arm deliberately not relaxed — ADR 0007). The MESSAGE arm is unchanged here in the token sense; the NICKNAME arm no longer dead-ends the name action — a dead-end-as-appearance name is now still reset to `Derpies` (the word simply isn't learned).
- **SPLIT (a word spread over spaces — NOW CLOSED, ADR 0009, 2026-09-17)**: `z w i f t` (the observed 2026-09-17 evasion) is now caught — `tokensForMatch` yields the collapsed run `zwift`, so a seeded `zwift` is a zero-ask fast delete and a new split word is LLM-learnable (the gate collapses the verdict's whitespace and anchors it to the collapsed run). **Remaining dead-end — punctuation-wedged single tokens:** a word wedged with INTERIOR punctuation in ONE token (`s.w.i.f.t`, `s/w/i/f/t`, `s(w)i(f)t`) is still NOT caught — `tokensForMatch` trims edge punctuation only, so it stays one token and does not collapse; the LLM judges it GIMMICK but the verdict cannot anchor. Closing it needs interior-punctuation collapse (a larger semantic change, deferred).
- **Frame-anchored verdict words / URL-only text (the step-9 gate, ADR 0007 — NARROWED by the emoji fix, ADR 0010)**: the anchor requirement now applies only when the post has **word-like** text tokens, so a word-less post (a mention + emoji, or a bare URL with no word-like text) is judged like an image-only post — a valid ASCII verdict word passes `wordValid` alone and the score decides (the LLM answers the most distinctive word of what the emojis/URL MEAN). The remaining dead-end is now ONLY for **non-ASCII** verdict words on a word-less post: arm (b) stays text-anchored on the posted-message word-like scope, and a word-less post has no word-like anchor, so a frame-only non-ASCII word is still rejected (the frame-only arm is deliberately not relaxed — ADR 0007). A word that appears ONLY in a frame of a TEXTED post (word-like tokens present) is still rejected by the anchor check (the word must be a token of the text). The URL-only relaxation remains operator-decision-pending.
- Image downloads are best-effort — a per-URL failure skips that URL (logged); when nothing downloads the ask degrades to text-only. The ask payload itself is bounded by the pi rpc image pipeline (identical-content dedupe, >1MB/>2048px resize+JPEG re-encode, 12MB raw per-ask cap) so a 10-attachment (or 25-boosted) message can never become a 46MB+ prompt.
- **Repeat-image re-judgment (the 4.6 fast delete was removed)**: an image whose CONTENT was previously LLM-judged is NOT a fast delete — its post goes into a FRESH pi ask (at most one list SELECT + one ask per post or edit), bounded by the pirpc per-ask image guard (byte-identical dedupe, >1MB / >2048px resize to 2048/JPEG q80, 12MB raw cap). There is no zero-ask deletion on any image state: N re-posts = N bounded asks in the shared pi queue.
- Referenced-message fetch is one hop (mention parity) — chains are not followed; a fetch failure (deleted/rate-limited) degrades to judging the posted message only, so a gimmick that lives ONLY in a deleted quote passes through.
- **Burst amplification**: no per-author coalescing or cooldown — N near-identical novel posts from a filtered user yield N serialized pi asks (the single pi RPC request channel is shared with the mention handler) plus N list SELECTs. A learned word's repetition is fast-path only; coalescing/rate limiting is out of scope per the spec.
- `make test-db` invalidates the migration tracker on the shared compose DB (see the `NOTE` on the Makefile target) — recreate with `docker compose down -v` or `DROP` the test-left objects before the next `make migrate`/`make setup`.

## Production acceptance (done-when)

With `TUGBOT_DERPIES_USER_IDS=163055057254875136` in `.env` and the `derpies` flag enabled in prod: (1) a message by that user containing a seeded gimmick word (e.g. `sw1ft`) is deleted within seconds with NO bot message, reaction, or gulag involvement; (2) a message containing a NEW respelling (e.g. `zswiftf`) that no list entry matches is sent to the pi RPC, and on a `SCORE:≥40` + `WORD:<word>` verdict the word is persisted to `derpies_gimmicks` with `source='llm'` (learn band) and the message is deleted when `SCORE ≥ T` (delete band) — the two are independent; (3) any later post containing `zswiftf` is deleted by the fast path with zero pi RPC asks; (4) a `mention + emoji` post with no word-like text (the observed dead end, e.g. `<@…> 💸 <:derpies:…> 🚵`) is judged like an image-only post — a `SCORE:95 WORD:zwift` verdict (the LLM answers the most distinctive word of what the emojis MEAN) passes the `wordValid`-only gate, learns `zwift`, and deletes when `SCORE ≥ T`; (5) an image attachment is downloaded (`Downloading image` lines) and joins the pi ask via `AskWithImages` — a `SCORE:≥40 WORD:<word>` on a word-less post deletes it and LEARNS the word (`wordValid` gate only), while a word valid but absent from a texted post's text AND its (quoted) reference is not learned (the anchor check rejects) but is still deleted when `SCORE ≥ T` (delete is independent of the learn); (6) a reply/quote re-quoting a seeded word deletes the CURRENT message on the fast path without retyping it; (7) a stored phrase (e.g. `buy me a bike` in `derpies_gimmick_phrases`) fast-deletes a matching post with zero pi asks; (8) every judged message writes a `derpies_decisions` row (read back via the `read_derpies_decisions` MCP tool); (9) a referenced-message fetch failure (deleted/rate-limited) degrades to judging the posted message only — logged, no flow abort.

## Out of scope (by spec)

- The Rust `derpies` module's reaction-removal behavior (dead; superseded by this feature's delete-only behavior).
- Any notification to `#the-gulag`, any bot message, any reaction.
- Per-user offense counters, rate limiting, or `SlowUserIDs`-style auto-gulag for derpies.
- **Score-model follow-ups (ADR 0010, v1 out of scope):** non-ASCII phrase tokens (v1 phrases are ASCII-only); `/gimmick` phrase subcommands (v1 curation is SQL-only); logging the nickname flow to `derpies_decisions` (v1: message flow only); a `derpies_decisions` prune/retention tool (v1: append-only, keep everything); a SPLIT word inside a phrase (v1: exact-consecutive match only — a split word inside a phrase falls to the slow path).
